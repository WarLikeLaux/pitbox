Pitbox держит переиспользуемый пул Git worktree для кодинг-агентов. Он бронирует свободный слот, записывает готовность ветки, сливает её по запросу и возвращает слот в пул. CLI и MCP-сервер предоставляют одни и те же операции.

Pitbox отвечает за состояние слотов и операции Git. Репозиторий сам решает, какие задачи идут в слоты, какие проверки запускать, когда проводить ревью, пушить и деплоить. Эти решения должны быть в инструкциях репозитория. Pitbox не запускает тесты, не следит за CI и не деплоит.

## Цикл работы

```text
основной чекаут      слот wt1           слот wt2
интеграция           task-ветка         свободен
```

1. Исполнитель вызывает `pitbox status`, затем `pitbox claim` без номера. Claim атомарно выбирает свободный worktree и печатает его путь.
2. Исполнитель следует правилам репозитория, коммитит задачу и вызывает `pitbox ready wt1`. Ready записывает ветку и точный HEAD в общем Git-каталоге. Маркер не означает, что тесты прошли.
3. По явной просьбе пользователя отдельная сессия интегратора вызывает `pitbox collect ready` или указывает нужные слоты. Collect отказывает, если основной чекаут грязный, находится не на основной ветке или слот изменился после ready.
4. Интегратор выполняет правила репозитория для проверок, CI, пуша и деплоя, затем вызывает `pitbox release wt1`. Release готовит слот к новой задаче.

Замечания до сборки исправляются в том же слоте. На время правок вызовите `pitbox unready wt1`, затем снова отметьте готовность. Если все слоты заняты, дождитесь освобождения.

Запуск агента из основного чекаута не делает его интегратором. Чтобы обычные задачи уходили в слоты, добавьте короткое правило в `AGENTS.md` репозитория или файл инструкций, который читает агент:

```md
- Для обычной задачи выполните `pitbox status` и `pitbox claim` без номера слота. Работайте в полученном worktree.
- Сессия, взявшая слот, остаётся его исполнителем. Проверьте работу в слоте, закоммитьте файлы задачи и выполните `pitbox ready`. Не деплойте, не собирайте и не освобождайте слоты, не пушьте основную ветку.
- Собирайте слоты только по явной просьбе пользователя в отдельной сессии. Следуйте правилам репозитория для проверок, CI, пуша и деплоя.
- Работа, явно назначенная в основной чекаут, следует обычным правилам доставки репозитория.
```

## Настройка

Нужны Bash, Git 2.31+ и Node.js для MCP. Внутри репозитория вызовите `pitbox setup`, чтобы создать три переиспользуемых слота рядом с основным чекаутом. Другой размер пула передаётся аргументом:

```bash
pitbox setup 5
pitbox status
```

Для репозитория на основной ветке отдельная инициализация и конфиг не нужны. Если ветка называется нестандартно или нужен постоянный размер пула, добавьте в репозиторий `.pitbox/config` только с этими параметрами:

```text
MAIN_BRANCH=custom
SLOTS=5
```

Pitbox читает эти значения как данные и не исполняет конфиг как shell-код. Из старого конфига с `READY_MODE`, `EVIDENCE`, `REQUIRE_PUSH` или `INTEGRATE_CHECKS` перед использованием этой версии нужно убрать эти параметры. Правила доставки перенесите в инструкции репозитория.

Репозиторий может добавить `.pitbox/setup.sh` для подготовки нового или обновлённого слота и `.pitbox/release.sh` для очистки освобождённого слота. Каждый скрипт получает путь слота в `$1`. Если `release.sh` отсутствует, release запускает `setup.sh`. Pitbox больше не генерирует скрипты под конкретный стек.

## Команды

| Команда | Действие |
|---------|----------|
| `pitbox setup [N]` | Создать и зарегистрировать фиксированный пул |
| `pitbox status` | Показать путь, ветку, грязные файлы, коммиты впереди и состояние каждого слота |
| `pitbox claim [slot\|branch-name] [branch-name]` | Атомарно забронировать свободный слот и создать task-ветку |
| `pitbox ready <slot> [note]` | Записать чистую task-ветку и её HEAD |
| `pitbox unready <slot>` | Снять маркер готовности на время правок |
| `pitbox collect <slot\|ready>` | Слить один слот или все помеченные в основную ветку |
| `pitbox release <slot>` | Сбросить слот на основную ветку и запустить release-хук |
| `pitbox deploy-guard` | Необязательная проверка: отказать, пока есть несобранный ready-слот |

Состояние слотов хранится в `pitbox/slots/` общего Git-каталога, вне worktree. Необязательный deploy guard проверяет только это состояние. Он не определяет роль вызывающего агента. Репозиторий может вызвать его из собственного скрипта деплоя.

## MCP и плагины

MCP-сервер передаёт вызовы CLI. Каждый инструмент требует `repo`, абсолютный путь к репозиторию или worktree: хост плагина может запускать сервер из кэша. Таймаут хука по умолчанию 120 секунд, он меняется через `PITBOX_TIMEOUT_MS`.

Для отдельного MCP-подключения используйте `node /path/to/pitbox/mcp/server.mjs`. Плагин содержит этот сервер и короткий скилл `workflow`.

Claude Code:

```text
/plugin marketplace add WarLikeLaux/pitbox
/plugin install pitbox@pitbox
```

Codex:

```text
codex plugin marketplace add WarLikeLaux/pitbox
codex plugin add pitbox@pitbox
```

MiniMax Code (mavis / mcode):

```bash
ln -sfn "$(pwd)/plugin" "$HOME/.minimax/plugins/pitbox"
mcode plugin marketplace upgrade
mcode plugin list
```

После публикации новой версии `main` вызовите `bash scripts/update-installed.sh` из чистого чекаута. Скрипт обновит Claude Code, Codex, MiniMax Code и отдельный CLI. Параметр `--only=claude|codex|mavis|cli` выбирает одну цель. Чтобы загрузить новый плагин, начните новую сессию агента.
