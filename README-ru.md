# pitbox

[![CI](https://github.com/WarLikeLaux/pitbox/actions/workflows/ci.yml/badge.svg)](https://github.com/WarLikeLaux/pitbox/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

[English](README.md) | Русский

Слой координации для параллельных кодинг-агентов: переиспользуемые worktree-воркеры, явная передача работы и детерминированная сборка. Один скилл плагина ведёт работу в слоте и интеграцию. Правила воркфлоу генерируются из политики репозитория, `pitbox guide` печатает их. `pitbox init` пишет только файлы `.pitbox/`.

## Зачем

Кодинг-агенты мешают друг другу в одном чекауте. Создавать worktree под каждую задачу просто, но остаются две проблемы: брошенные worktree копятся как мусор на диске, и у агента нет стандартного способа сказать «задача готова, забирайте».

pitbox отвечает тремя решениями. Worktree здесь лишь рантайм. pitbox владеет жизненным циклом задачи вокруг них: claim, работа, ready, collect, release.

- Фиксированный пул из двух-трёх слотов, созданный один раз рядом с чекаутом и переиспользуемый вечно. Никаких спавнов под задачу, никаких остатков, установка зависимостей оплачивается один раз на слот.
- Маркер готовности. Агент слота заканчивает работу пометкой слота готовым, интегратор собирает только помеченные слоты, а слово пользователя всегда перекрывает маркер. Состояние слотов лежит в git-директории в `pitbox/`, поэтому не мусорит в `git status` и не коммитится случайно.
- Настройки слотов для каждого репозитория. `pitbox guide` показывает настройки из `.pitbox/config`: когда ставить ready, что показать как результат, нужно ли пушить task-ветки. Инструкции репозитория решают, какие задачи идут в слоты и как доставлять результат.
- Разделение ролей. Агенты слотов не мёржат и не деплоят. Сессия, работавшая в слоте, заканчивает на ready. Другая сессия собирает, пушит и освобождает слоты. Деплой выполняется только тогда, когда его требует репозиторий.

## Как это работает

```
your-repo/            your-repo-wt1/       your-repo-wt2/       your-repo-wt3/
main checkout         слот wt1             слот wt2             слот wt3
интеграция            агент + task-ветка   агент + task-ветка   запасной
```

- Инструкции репозитория могут направлять в слот даже единственную задачу. Запуск агента из основного чекаута не делает его интегратором.
- Пока в слотах идёт работа, используйте основной чекаут для интеграции в отдельной сессии.
- Агент слота берёт слот через `pitbox claim` (команда атомарно бронирует свободный слот и создаёт task-ветку), проверяет работу внутри слота, коммитит файлы задачи и помечает ветку готовой.
- Интегратор собирает готовые слоты, следует правилам доставки репозитория и возвращает слоты в пул. `INTEGRATE_CHECKS=auto|full|ci` задаёт его локальные проверки.

По умолчанию (`READY_MODE=auto`) агент слота проверяет, коммитит и помечает работу готовой без ожидания ревью. Если перед ready нужно подтверждение, задайте `READY_MODE=confirm`. Пользователь просит отдельную сессию собрать слоты, когда результат его устраивает. `pitbox guide` показывает настройки слотов. Исключения из правил прямой работы, например «деплой до коммита» или ревью до коммита, нужно явно записать в `AGENTS.md` репозитория. Pitbox не читает и не меняет этот файл.

Если вы запускаете агентов из основного чекаута и хотите, чтобы они сами брали свободный слот, добавьте в `AGENTS.md` репозитория:

```md
- Для обычной задачи выполните `pitbox status` и `pitbox claim` без номера слота. Работайте в полученном worktree.
- Сессия, взявшая слот, остаётся его исполнителем. Проверьте работу в слоте, закоммитьте только файлы задачи и выполните `pitbox ready`. Не деплойте, не собирайте и не освобождайте слоты, не пушьте основную ветку.
- Собирайте слоты только по явной просьбе пользователя в отдельной сессии, которая не работала в слоте. Деплойте только тогда, когда это требуется репозиторию.
- Работа, явно назначенная в основной чекаут, следует обычным правилам доставки репозитория.
```

В том же чате можно продолжать работу. Замечания к готовой задаче до сборки агент исправляет в её слоте: на время правок снимает маркер через `unready`, чтобы слот не рекламировал готовность, и снова отмечает готовой после правки. После сборки и освобождения слота новую задачу агент начинает с проверки статуса и `pitbox claim`. Номер слота указывать не нужно. Отдельная новая задача до сборки требует другого свободного слота.

## Быстрый старт

Нужны только bash, git 2.31+ и node для MCP-сервера. Windows работает через WSL.

```bash
curl -fsSL https://raw.githubusercontent.com/WarLikeLaux/pitbox/main/bin/pitbox -o ~/.local/bin/pitbox
chmod +x ~/.local/bin/pitbox
```

Подготовьте репозиторий один раз:

```bash
cd your-repo
pitbox init      # пишет шаблоны .pitbox/
pitbox setup     # создаёт ../your-repo-wt1 .. wt3 и ставит зависимости в каждый
```

Маркеры слотов пишутся в git-директорию (`pitbox/slots/` внутри `.git`), так что глобальный git ignore не нужен.

Повседневные команды:

| Команда | Что делает |
|---------|------------|
| `pitbox init [--stack S] [--force]` | Пишет шаблоны `.pitbox/` и не меняет `AGENTS.md` (стеки: `bun`, `php-docker`, автоопределение) |
| `pitbox setup [N]` | Создаёт пул слотов, по умолчанию три |
| `pitbox claim [branch-name]` | Атомарно бронирует свободный слот и создаёт task-ветку (сам выбирает слот, при необходимости можно указать слот перед веткой) |
| `pitbox status` | Ветка, грязные файлы, коммиты впереди main, состояние слотов (work/ready/collected) и строка активной политики |
| `pitbox ready <slot> [note]` | Помечает задачу слота готовой, фиксирует HEAD ветки, отказывает на грязном слоте или заглушке ветки |
| `pitbox unready <slot>` | Снимает маркер готовности на время правок по замечаниям, слот возвращается в работу до нового ready |
| `pitbox collect <slot\|ready>` | Мёржит task-ветку слота в основную ветку через `--no-ff`, отказывает при грязном основном чекауте, ветке не main и слотах, изменившихся после маркера, собранные слоты пропускает до release |
| `pitbox release <slot>` | Сбрасывает слот на main, удаляет влитую ветку, гоняет release-хуки |
| `pitbox ci` | Статус CI запушенного коммита main: зелёный (код 0), красный (1), в работе (2) |
| `pitbox deploy-guard` | Ненулевой выход, пока слот висит ready и не собран, для вызова из деплой-скриптов как гварда |
| `pitbox guide` | Печатает правила воркфлоу этого репозитория, отрендеренные из `.pitbox/config` |

## MCP-сервер

MCP-сервер это zero-dependency stdio-фасад над CLI. Инструмент `guide` возвращает весь воркфлоу, отрендеренный из политики репозитория, а зависший хук `.pitbox` не может заблокировать вызов навсегда (таймаут 120 с по умолчанию, меняется через `PITBOX_TIMEOUT_MS`). Скилл `workflow` выбирает режим слота или интегратора.

Подключите любой MCP-клиент:

```json
{
  "mcpServers": {
    "pitbox": {
      "command": "node",
      "args": ["/path/to/pitbox/mcp/server.mjs"]
    }
  }
}
```

Claude Code:

```bash
claude mcp add pitbox -- node /path/to/pitbox/mcp/server.mjs
```

Codex (`~/.codex/config.toml`):

```toml
[mcp_servers.pitbox]
command = "node"
args = ["/path/to/pitbox/mcp/server.mjs"]
```

Хост плагина может запускать MCP-сервер из своего кэша. Поэтому каждый инструмент, работающий с репозиторием, требует параметр `repo`: абсолютный путь к нужному репозиторию или worktree. При подключении сервер передаёт агенту шаги онбординга и правила работы. В новом репозитории вызовите `init` с `repo`, проверьте и закоммитьте `.pitbox/`, затем вызовите `setup` с тем же `repo`.

### Справочник инструментов

| Инструмент | Назначение |
|------------|------------|
| `guide` | Правила воркфлоу из политики репозитория, вызовите один раз перед остальными |
| `status` | Состояние пула слотов и активная политика, вызывайте перед сборкой, для новой задачи используйте `claim`, не бронируйте слот руками |
| `claim` | Атомарно забронировать свободный слот и создать в нём свою task-ветку |
| `setup` | Создать фиксированный пул слотов, никаких спонтанных worktree |
| `ready` | Помечать слот готовым, фиксирует HEAD ветки в git-директории, отказывает на грязном слоте или заглушке, самому не мёржить |
| `collect` | Интегратор: влить ветку слота, или `ready` для всех помеченных, отказывает при грязном основном чекауте и ветке не main, собранные слоты пропускает |
| `ci` | Интегратор: статус CI запушенного коммита main, зелёный, красный или в работе |
| `release` | Интегратор: вернуть собранный слот в пул |
| `init` | Написать шаблоны `.pitbox/` без изменений `AGENTS.md` |

## Плагины для Claude Code, Codex и MiniMax Code

Плагин содержит MCP-сервер и один скилл `workflow` с режимами слота и интегратора. Агент может выбрать его при работе в слоте Pitbox или по просьбе собрать готовые слоты.

Claude Code:

```
/plugin marketplace add WarLikeLaux/pitbox
/plugin install pitbox@pitbox
```

Codex (0.157+):

```
codex plugin marketplace add WarLikeLaux/pitbox
codex plugin add pitbox@pitbox
```

MiniMax Code (mavis / mcode, 0.5+):

```bash
# Локальный маркетплейс — это каталог `directory ~/.minimax/plugins`.
# Симлинк или копия плагина туда, затем обновить снимок.
ln -sfn "$(pwd)/plugin" "$HOME/.minimax/plugins/pitbox"
mcode plugin marketplace upgrade
mcode plugin list    # покажет `[*] pitbox@local enabled`
```

`mcp.json` плагина использует спек-переменную `${PLUGIN_ROOT}`, поэтому плагин сам подключает свой MCP-сервер во всех поддерживаемых хостах. На старых сборках Codex без поддержки плагинов зарегистрируйте сервер вручную, как показано выше, и скопируйте `plugin/skills/workflow` в свою директорию скиллов.

### Обновление локальных установок

Если изменился `plugin/`, повысьте версию одновременно в `plugin/plugin.json`, `plugin/.claude-plugin/plugin.json` и `.claude-plugin/marketplace.json`. При прежней версии Claude оставит старую копию в кэше. Прогоните `bash scripts/smoke.sh`, закоммитьте изменения и запушьте `main`. После этого обновите установку на этой машине:

```bash
bash scripts/update-installed.sh
```

Скрипт требует чистый чекаут на опубликованном коммите `origin/main`. Он обновляет маркетплейсы Codex, Claude и MiniMax Code, все установленные плагины и `~/.local/bin/pitbox`, затем сравнивает кэши плагина с исходниками. Если CLI стоит в другом месте, задайте `PITBOX_CLI_TARGET`; если плагин MiniMax Code в другом каталоге — `PITBOX_MAVIS_TARGET`. Чтобы обновить только один таргет, передайте `--only=claude|codex|mavis|cli`. Новые версии плагинов загрузятся в новых сессиях Codex, Claude и mavis.

## Конфигурация репозитория

pitbox глобальный, специфика репозитория живёт в `.pitbox/` рядом с кодом.

- `.pitbox/config`: переменные шелла. `MAIN_BRANCH=<branch>` перекрывает автоопределение (порядок: конфиг, `origin/HEAD`, текущая ветка). `SLOTS=<N>` задаёт размер пула для `setup` без аргумента (по умолчанию 3), `status` предупреждает о расхождении. `READY_MODE=auto|confirm` задаёт момент установки ready. `EVIDENCE=auto|screenshot|requests|none` задаёт способ показать результат. `REQUIRE_PUSH=1` требует запушенную task-ветку до ready. `INTEGRATE_CHECKS=auto|full|ci` запускает полные локальные проверки после мёржа с ручным разрешением конфликта по умолчанию, после каждого мёржа с `full` или оставляет их CI с `ci`. Необходимость деплоя определяют инструкции репозитория.
- `.pitbox/setup.sh`: вызывается с директорией слота как `$1` после добавления worktree и на release. Шаблон `bun` гоняет `bun install --frozen-lockfile`, шаблон `php-docker` гоняет `composer install`.
- `.pitbox/release.sh`: опциональная доп. уборка на release, иначе используется `setup.sh`.

Состояние слотов живёт в общем git-каталоге, видимом из каждого worktree и невидимом для `git status`: `pitbox/slots/<name>.path` регистрирует слот, `pitbox/slots/<name>.ready` это маркер готовности, `pitbox/slots/<name>.collected` появляется после успешного мёржа и заставляет повторный `collect` пропускать слот до release.

В репозиториях, настроенных старой версией pitbox, переименуйте `.slots/` в `.pitbox/` перед запуском нового CLI. Старый каталог больше не читается. Маркер `TASK_READY.md` из pitbox до 0.4 импортируется в новое состояние автоматически при первой команде.

`pitbox init` пишет эти шаблоны и определяет стек по `composer.json` и `bun.lock` или `package.json`. Шаблоны стеков естественное место для контрибьюторов новых стеков.

Для php + docker проектов параллельным слотам нужна изоляция compose на слот: свой `COMPOSE_PROJECT_NAME` на слот, уникальные хост-порты и никаких фиксированных `container_name` в compose-файлах. Шаблон печатает об этом напоминание.

## Заметки

- Слоты живут соседними директориями: `../your-repo-wt1` и так далее, рядом с чекаутом.
- Мёржи специально `--no-ff`, пачки задач остаются видимыми в истории.
- Здесь нет конфликта с нативными worktree-механиками конкретных агентов. Сессии Claude Code могут использовать встроенную worktree-изоляцию, pitbox это общий пул и процедура сборки для всех остальных.
- npm-пакета пока нет, ставьте из клона. Поставьте звезду, если нужен.
